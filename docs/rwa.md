# 마루 카드 NFT 실행 가이드

2026-11-28 구현. [설계안](./rwa-design.md)을 바탕으로 컨트랙트·자체 x402 RWA 구매·DB 동기화·판매/인출 화면을 추가했습니다. **실물 보관 기록은 합성 데모이며 실제 보관·감정·배송·법적 권리 검증을 제공하지 않습니다.** 체인의 NFT와 테스트 tOKRW 이동은 실제입니다.

## 실행

Node 24, pnpm, Foundry의 `forge`가 필요합니다. 기존 [마루 환경](./maroo.md)의 DB·서버 구매 지갑을 준비하세요.

```powershell
pnpm install
pnpm db:migrate
pnpm rwa:build
pnpm rwa:deploy
pnpm facilitator:init
pnpm facilitator:up
pnpm dev
```

`rwa:deploy`는 새 운영 지갑에 구매 지갑으로부터 100 테스트 tOKRW를 충전해 컨트랙트 배포·민팅·판매 예치의 가스비로 사용합니다. 이 충전은 카드 구매가 아니며 기존 구매 정책 예산에 포함하지 않습니다. 배포 단계와 해시를 공개 manifest에 기록합니다. 재실행은 완료된 단계를 재사용하며 판매 완료·소각된 NFT를 초기화하거나 재발행하지 않습니다. 구매 지갑과 운영 지갑을 다른 프로세스에서 동시에 사용하지 마세요.

루트 `.env`에 운영 개인키·활성 플래그·NFT/마켓 주소·서명자·코드 해시·배포 블록을 기록합니다. 개인키는 퍼실리테이터에 전달하지 않습니다. 원문 서명은 DB·로그·LLM에 저장하지 않습니다. 해시 기록 후 방송 여부가 불명확하면 자동 재전송하지 않고 기존 해시를 확인합니다. 배포가 중단되면 manifest와 체인을 대조한 뒤 재실행하세요. 해시 없는 새 트랜잭션으로 대체하지 않습니다.

## 화면과 역할

`/rwa` 또는 서비스 메뉴의 NFT에서 토큰·권리자 지갑·보관 상태·탐색기·판매 대금을 확인합니다. 구매는 ‘에이전트에서 NFT 매물 보기’로 대화 입력을 준비한 뒤 전송하고, 반환된 NFT 구매 버튼으로 승인합니다. 조회만으로 결제하지 않습니다. NFT 매물은 채팅에서 우선 정렬하고 일반 매물과 구분해 표시합니다.

보유자는 ‘이 NFT 판매 승인’ 후 ‘판매 등록·NFT 예치’를 실행합니다. 판매 취소는 온체인 NFT 반환을 동반합니다. 일반 카드의 DB 매물 등록·취소 API로 NFT를 처리할 수 없습니다. 구매 중인 매물은 결제 복구 후 취소하며 서명 전 예약만 있는 경우 기존 Trading 해제 절차를 사용합니다.

현재 Web 역할은 기존 `WEB_DEMO_ROLE=buyer|seller` 설정을 따릅니다. 구매자 화면은 전용 에이전트 지갑, seller 화면은 별도 운영 지갑을 사용합니다. 판매 대금은 마켓의 proceeds이며 ‘내 지갑으로 출금’으로 실제 tOKRW를 수령합니다. 기존 일반 카드의 DB 판매 대금·수납 주소와 구분합니다. 첫 데모에서 운영 지갑은 분리된 컨트랙트 역할을 함께 보유합니다. 다중 사용자 지갑 등록·서명 위임 UI는 범위 밖입니다.

인출은 소유자 요청 → NFT 잠금 → 보관자 반출 승인 → 완료·소각입니다. 소유자는 승인 전 취소할 수 있습니다. 보관자는 미반출 시 승인을 취소해 소유자가 요청을 취소하도록 할 수 있습니다. 소각 전에 UI의 확인 항목을 선택합니다. 실물 배송 업무는 시뮬레이션입니다. NFT 전체 비상 중지는 일반 NFT 이전도 막으므로 마켓 반환이 필요하면 관리자가 상황 확인 후 해제해야 합니다. 마켓만 중지했을 때 판매 취소와 판매 대금 출금은 가능합니다.

## x402와 복구

기존 `maroo-native` EOA 송금과 별도인 자체 x402 v2 scheme `maroo-rwa`를 사용합니다. 요구의 payTo는 마켓이며 서명된 EIP-712 견적과 calldata 해시를 포함합니다. 에이전트와 퍼실리테이터는 주소·배포 코드 해시·견적·함수 호출·구매자·NFT·가격·만료·nonce·가스를 검증합니다. 임의 컨트랙트 호출·approve·multicall은 구매 지급으로 받지 않습니다. ERC20 exact 표준 scheme과 호환된다는 의미는 아닙니다.

buyListing 한 트랜잭션 안에서 NFT 이전과 판매 대금 적립이 함께 성공하거나 함께 revert합니다. 판매 대금을 외부 지갑에 즉시 보내지 않고 출금 잔액으로 적립하므로 판매자의 송금 수신 실패로 구매 전체가 막히지 않습니다. 구매자 수신 콜백 실패 시 전체 revert합니다. 구매 가스비는 별도이며 현재 RWA 서명 상한은 1,000,000 gas / 10 tOKRW, 실제 추정치를 사용합니다. 정책 사용 예산에는 구매 금액만 반영합니다.

SETTLED는 해당 마켓의 PurchaseExecuted와 NFT Transfer를 모두 검증한 뒤 반영합니다. 체인 성공 후 DB 실패는 기존 Payment/Trading 복구로 재처리합니다. Indexer는 finalized 로그·blockHash·txHash·logIndex를 보존하고 지갑 간 직접 NFT 이전도 반영합니다. 마켓 예치 중 권리자는 판매자, 인출 잠금 중 권리자는 요청자입니다.

퍼실리테이터 응답 유실로 Core에 해시가 없으면 Indexer가 같은 quoteId의 PurchaseExecuted에서 기존 결제 해시를 찾아 연결합니다. 이후 Payment가 영수증을 검증하며 새 서명·새 송금은 만들지 않습니다. 확정 실패 시 가격은 결제되지 않지만 가스비는 발생합니다. 작업 응답이 유실되면 `/api/rwa/actions/:id`로 기존 ID만 확인하세요.

블록 해시 불일치·누락 복구 시 API를 중지한 뒤 아래 명령으로 로그 사본을 재구성합니다. 기존 거래·예산·NFT를 삭제하지 않습니다.

```powershell
pnpm rwa:sync -- --rebuild
```

## API와 모듈 경계

- `GET /api/rwa`: 인증된 데모 역할의 자산·카드·판매 대금·배포 정보.
- `POST /api/rwa/actions`: UUID Idempotency-Key와 고정 kind·assetId·listingId·redemptionId·price만 수신. 임의 주소·개인키·calldata 수신 금지.
- `GET /api/rwa/actions/:id`: 해당 사용자 요청의 기존 상태 조회.
- 민팅은 공개 API 없이 배포/데모 시드에서 수행합니다. 보관자 작업은 seller 권한을 요구합니다.
- 기존 MCP quote/execute/status와 정책·예산·Trade를 재사용하고, Payment의 선택적 요구 생성 팩토리와 Trading의 NFT 업무 가드·조회 장식만 확장합니다.

## 검증 기록

[이브이 NFT 실제 구매](https://explorer-testnet.maroo.io/tx/0x971d56e16cc5f38eadc51d2d5b6d739906e00a550d8dd1a822b287facece301d): 5 tOKRW, 가스비 1.340541 tOKRW. Web BFF→Agent→MCP→퍼실리테이터→컨트랙트를 경유했고 NFT #3의 ownerOf가 구매 지갑으로 바뀌었습니다. DB Trade `b2ba1734-212a-438f-9dbc-aaf3ab83d834`, 보유 카드 증가와 동일 요청 재제출의 중복 지급 방지를 확인했습니다.

판매 재등록·취소, 인출 잠금·반출 승인·승인 취소·요청 취소를 실제 테스트넷에서 수행하고 #3을 구매자 보유 상태로 복원했습니다. [판매 대금 5 tOKRW 출금](https://explorer-testnet.maroo.io/tx/0x02f38f93900a319cb68195fe626d8c612d527e90b3552657d14746c64609e756) 후 마켓의 운영 지갑 출금 잔액은 0입니다. 오프라인 로그 재구성도 송금 없이 검증했습니다. 최종 소각은 로컬 컨트랙트 테스트로 검증하고 테스트넷의 구매 NFT는 소각하지 않았습니다.

```powershell
forge test --root contracts -v
pnpm test
pnpm typecheck
pnpm build
```

브라우저 자동화가 현재 URL을 식별하지 못해 직접 화면 캡처 검증은 수행하지 못했습니다. 화면의 렌더링·입력 라벨·이미지·데모 고지·업무 경로 제한은 자동 테스트로 확인합니다. 실제 카드 보관·배송·운영 보안 감사·PCL 규제 proxy 연동은 이 데모의 완료 범위에 포함하지 않습니다.

최종 검증: PostgreSQL을 포함한 TypeScript 테스트 355개, Solidity 테스트 15개(중복 실물 식별자 퍼즈 256회 포함), 전체 타입 검사·빌드, 별도 퍼실리테이터 컨테이너의 정상 실행을 확인했습니다. 동시성 테스트에서 확인한 Prisma 드라이버의 TransactionWriteConflict도 기존 제한 재시도 절차에 포함했습니다.
