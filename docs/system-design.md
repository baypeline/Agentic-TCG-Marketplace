# Agentic TCG Marketplace 시스템 설계서

**버전:** v2.2 — 거래·예산·실행 수명 합의 반영

**기준일:** 2026년 11월 24일

**프로젝트:** AI Agent × MCP × x402 × TCG Trading

원본은 사용자가 제공한 시스템 설계서 v2.1입니다. v2.2는 이번 대화에서 사용자와 확정한 업무 규칙을 반영한 저장소 개정본입니다. 문서 개정은 구현 완료를 의미하지 않습니다. 세부 결정과 현재 코드의 차이는 [합의 사항 및 구현 차이](decisions.md), 호출 계약은 [API 계약서 v2.1](api-contract.md)을 함께 확인하세요.

## 1. 프로젝트 목표

본 프로젝트는 AI Agent가 트레이딩 카드의 시장가격과 적정가를 분석하고, 사용자가 사전 승인한 예산과 조건에 따라 자율적으로 구매한 뒤, x402 결제를 통해 거래를 완료하는 시스템을 구현한다.

핵심 검증 질문은 다음과 같다.

- AI Agent가 카드 데이터와 가격 정보를 기반으로 구매 판단을 내릴 수 있는가?
- Agent가 MCP Tool을 이용해 외부 거래 시스템을 안전하게 조작할 수 있는가?
- Agent가 사용자 승인 범위 내에서 x402 지급을 실행할 수 있는가?
- 결제 완료와 카드 소유권 이전을 일관성 있게 처리할 수 있는가?

이 시스템은 Agent 간 직접 협상이 아닌 **중앙 마켓플레이스 기반 거래 시스템**이다.

## 2. MVP 범위

### 2.1. 포함 기능

1. 포켓몬 TCG 카드 데이터 검색 및 가격 분석
2. 내부 모의 카드 인벤토리
3. 판매자의 고정가 매물 등록
4. 구매자의 고정가 즉시 구매
5. 구매자의 매수 지정가 주문
6. 구매자의 시장가 구매
7. Agent의 사전 승인 정책 기반 구매 판단
8. MCP Tool을 통한 주문·결제 기능 호출
9. Agent 전용 EOA에서 테스트 USDC 결제
10. 결제 완료 후 내부 카드 소유권 이전
11. 웹에서 Agent 상태·거래 내역 확인

### 2.2. 제외 기능

- 판매 지정가 및 시장가 주문
- 양방향 오더북 및 매도 주문 매칭
- 부분 체결 또는 카드 다량 주문
- Agent 간 직접 협상
- 온체인 카드 NFT 발행
- 판매자에게 실제 USDC 지급
- 사용자 간 현금 출금
- 별도 에스크로 스마트컨트랙트
- 여러 거래소 간 자동 차익거래
- 완전한 상용 사용자 인증·KYC 시스템

## 3. 거래 모델

### 3.1. 거래 대상

MVP는 포켓몬 TCG를 우선 대상으로 한다.

카드는 다음 두 개념으로 구분한다.

**CardVariant**

특정 세트, 카드 번호, 언어, 에디션, 보존 상태를 가진 거래 가능한 카드 유형.

**InventoryItem**

실제 모의 소유권을 갖는 개별 카드 1장. 거래 후에도 동일한 InventoryItem UUID를 유지하고 ownerId를 구매자로 변경하며 상태는 AVAILABLE로 둡니다. TRANSFERRED 상태는 제거하고 이전 소유자·가격·완료 시각은 Trade로 보존합니다. 소유권 변경과 Trade 저장은 같은 DB 트랜잭션에서 정확히 한 번 처리합니다.

동일 CardVariant에 속하는 InventoryItem은 여러 개 존재할 수 있다.

### 3.2. 매물 구조

판매자는 자신이 소유한 InventoryItem 하나를 고정 가격으로 등록한다.

하나의 InventoryItem은 동시에 하나의 활성 매물에만 등록할 수 있다.

### 3.3. 구매 전략

**고정가 즉시 구매**

Agent가 특정 매물을 선택하여 표시된 가격으로 구매한다.

**매수 지정가**

Agent가 특정 CardVariant와 최대 구매 가격을 설정한다. 가격 조건을 충족하는 매물이 나타나면 매칭 후보가 된다.

**시장가 구매**

Agent가 현재 활성 매물 중 최저가를 조회하고, 자신에게 허용된 최대 가격 이하라면 즉시 구매를 시도한다.

시장가는 무제한 가격 구매를 의미하지 않는다. 반드시 최대 구매 가격을 포함한다.

### 3.4. 공통 거래 제약

- 거래 수량은 1장이다.
- 부분 체결은 지원하지 않는다.
- 가격 우선, 동일 가격이면 등록 시간 우선을 적용한다.
- 판매자 카드 중복 등록·예약·판매를 방지한다.
- 실제 카드 이동은 결제 정산 이후에만 수행한다.
- 지정가 주문은 Agent가 온라인이고 정책이 유효할 때만 신규 매칭을 실행한다.
- 시장가 주문은 매칭 가능한 매물이 없으면 즉시 종료한다.

```
사용자 브라우저
     │
     ▼
Next.js Web / BFF
     ├───────── REST ─────────► Fastify Core API
```

## 7. 패키지 통합 원칙

### 7.1. Fastify Plugin

Fastify 서버에 연결되는 담당 패키지는 플러그인을 제공한다.

- Aggregator Plugin
- Valuation Plugin
- Trading Plugin
- Payment Plugin
- MCP Plugin

플러그인의 역할은 HTTP 엔드포인트 등록, 의존성 연결, 자원 초기화다.

핵심 비즈니스 로직은 Fastify에 종속되지 않는 Service로 구현한다.

### 7.2. 명시적 의존성 주입

각 모듈은 필요한 외부 Service를 인수로 전달받는다.

Fastify Decorator를 모듈 간 비즈니스 의존성의 유일한 통신 수단으로 사용하지 않는다.

### 7.3. 데이터베이스

하나의 PostgreSQL 및 공통 Prisma Client를 사용한다.

논리적 스키마는 `auth`, `catalog`, `market`, `agent`, `trading`, `payment`로 구분한다.

DB 스키마·마이그레이션은 `packages/db`에서 관리하고, 담당 모듈이 자신에게 할당된 모델의 변경안을 제출한다.

Prisma Client 생성과 DB 연결 초기화는 통합 호스트에서 수행한다.

### 7.4. 패키지 공개 인터페이스

모든 패키지는 `src/index.ts`를 통해 공개 인터페이스를 export한다.

다른 패키지의 `src/internal/*`, Repository, 비공개 Prisma 구현을 직접 import하지 않는다.

공통 요청·응답 스키마는 `packages/contracts`에서 관리한다.

## 8. 거래 핵심 흐름

### 8.1. 고정가 구매

1. Agent가 카드·매물 정보를 조회한다.
2. Agent가 적정가와 승인 정책을 검토한다.
3. Agent가 특정 고정가 매물을 선택한다.
4. Trading이 매물과 InventoryItem을 임시 예약한다.
5. Payment가 거래 금액·Agent 예산을 검증한다.
6. Agent가 x402 지급 승인을 서명한다.
7. Facilitator를 통해 지급을 정산한다.
8. Trading이 InventoryItem 소유권을 변경한다.
9. 거래 기록을 저장하고 Agent에게 결과를 통보한다.

### 8.2. 지정가 구매

1. Agent가 CardVariant와 최대 구매 가격을 지정한다.
2. Trading이 대기 중인 BuyOrder를 저장한다.
3. 활성 매물 중 가격 조건을 만족하는 후보를 조회한다.
4. Agent가 온라인이고 정책이 유효하면 구매 실행을 시도한다.
5. 이후 절차는 고정가 구매와 동일하다.

Agent를 명시적으로 중단하면 대기 지정가 주문은 PAUSED로 전환합니다. 이미 확보한 결제 미제출 예약은 자동 해제하지 않고 결제를 보류하며 원래 expiresAt을 유지합니다. 결제 제출 승인 이후에는 예약과 결제 복구를 유지합니다. 재개 시 최신 정책과 예산을 재검증합니다.

### 8.3. 시장가 구매

1. Agent가 CardVariant와 최대 가격을 전달한다.
2. Trading이 현재 최저가 매물을 찾는다.
3. 매물이 없거나 가격 상한을 초과하면 종료한다.
4. 매물을 예약하고 x402 결제를 진행한다.

시장가 주문은 오더북에 남지 않는다.

## 9. 결제 모델

### 9.1. 지갑

Agent는 전용 EOA 지갑을 사용한다.

사용자는 테스트 USDC를 Agent 지갑으로 이전한다.

Agent의 개인키는 Agent Runtime의 보안 설정으로 관리하며, 브라우저나 DB에 평문으로 저장하지 않는다.

### 9.2. 수납

MVP의 실제 테스트 USDC는 플랫폼 수납 지갑으로 이전된다.

판매자의 모의 판매 수익은 완료된 Trade의 판매 가격을 집계합니다. 별도의 가용 잔액을 중복 관리하지 않으며 동일한 Trade를 중복 집계하지 않습니다. 결제만 성공하고 소유권 이전이 진행 중이면 확정 수익에 포함하지 않습니다. 프론트에는 “모의 판매 수익 · 출금 불가”로 표시합니다.

### 9.3. 결제 상태

```
CREATED
  → REQUIRED
  → SIGNED
  → VERIFYING
  → SETTLING
  → SETTLED

오류:
FAILED
UNKNOWN
```

이 상태들은 SDK 원시 응답과 구분해 저장합니다. 결제 상태와 거래 상태도 분리합니다. 결제 SETTLED 시 예산 예약액을 사용 완료액으로 전환하고, 소유권 이전 전까지 “결제 완료 · 거래 처리 중”으로 표시합니다. 소유권 이전과 Trade 저장까지 완료해야 “구매 완료”입니다. 추가 결제 없이 거래 반영만 멱등 재시도하며 복구가 지연되면 운영자 확인 대상으로 넘기고 카드는 보호합니다.

### 9.4. 소유권 이전

Payment의 `SETTLED` 확인 전에는 Trading이 소유권을 이전하지 않는다.

Payment 정산 완료와 Trading DB 반영은 원자적 단일 트랜잭션이 아니므로, 정산 증빙을 보존하고 체결 처리를 멱등하게 재시도한다.

## 10. 안전성 및 장애 복구

**중복 구매 방지**

InventoryItem 단위로 유효한 예약을 하나만 허용한다.

**중복 결제 방지**

Match ID에 결제 의도를 결합하고, 재시도 시 기존 결제 시도를 조회한다.

**결제 결과 불명**

UNKNOWN이면 새 결제 시도·지급 서명을 만들지 않습니다. 카드와 예산 예약을 유지하고 마켓플레이스 서버가 기존 증빙으로 조회·복구합니다. 프론트는 “결제 확인 중”으로 표시하고 재결제를 차단합니다. 시간 경과만으로 실패 처리하지 않습니다. 성공 확인 시 거래 반영을 진행하고, 확정 실패 시 카드 예약 해제·예산 반환을 수행합니다. 장기 미확정은 운영자 확인 대상으로 넘기되 결과 확정 전 보호 상태는 유지합니다.

**결제 성공 후 DB 오류**

Payment는 SETTLED로 유지하고, Trading의 소유권 이전만 재실행한다.

**예약 만료**

정책 변경이나 Agent 중단만으로 기존 미제출 예약을 자동 해제하지 않습니다. 최신 정책에 어긋나거나 Agent가 중단됐으면 결제를 보류하고 프론트에 사유와 잔여 시간을 표시합니다. 보류 중에도 원래 expiresAt은 흐르며 자동 연장하지 않습니다. 만료 시 예약을 해제합니다. 실제 외부 정산 요청 직전에 서버가 최신 정책·예산·예약 유효성을 검사하고, 결제 시도·예산 예약·카드 보호 상태·적용 정책 버전을 같은 DB 트랜잭션에 저장합니다. 이 제출 승인이 확정된 예약은 TTL로 해제하지 않습니다. 저장 후 외부 정산 요청을 전송합니다.

**Agent 오프라인**

Agent 실행과 LLM 작업의 수명은 서버가 관리합니다. 브라우저 종료·네트워크 단절·SSE 연결 종료는 Agent 실행 중단 사유가 아닙니다. 브라우저는 상태를 조회·구독하고 재접속 시 기존 실행 상태를 받습니다. 명시적 중단·실행 기한 만료·정책 비활성화 시 신규 거래 실행을 중지합니다. 대기 주문은 PAUSED, 미제출 예약은 원래 TTL을 유지한 결제 보류, 제출된 결제는 정산·복구 계속으로 처리합니다. 명시적 사용자 제어 요청과 단순 연결 종료를 구분합니다.

### 10.1. 정책 식별자·예산·동시 처리

- 정책마다 UUID id와 version을 부여합니다. 수정은 같은 id의 새 version이며 이전 버전을 보존합니다.
- 세션은 policyId로 정책을 참조하고 결제 제출 승인에는 적용 policyId·policyVersion을 기록합니다.
- 총예산·사용 완료액·결제 예약액은 정책 ID 단위로 누적합니다. 재시작·새 세션·정책 수정으로 초기화하지 않으며 같은 정책을 사용하는 여러 세션이 공유합니다.
- 사용 가능 예산 = 총예산 − 사용 완료액 − 결제 예약액입니다. 결제 미제출 카드 예약만으로는 이 결제 예약액에 포함하지 않습니다.
- 총예산을 사용 완료액 + 결제 예약액 미만으로 낮추는 변경은 거부합니다. 예산 검사는 지갑 잔액 검사와 별개입니다.
- 정책 변경과 결제 제출 승인은 서버 DB의 확정 순서를 따릅니다. 정책 변경이 먼저면 최신 조건을 검사해 결제를 보류할 수 있고, 제출 승인이 먼저면 해당 결제를 보호·복구하며 새 정책은 이후 제출 승인부터 적용합니다.
- 정책이 바뀌어도 기존 카드 예약을 자동 취소하지 않습니다. 조건 위반은 결제 보류와 프론트 알림으로 처리합니다.

### 10.2. 가격 자료와 미매칭

가격 상한만 있는 구매는 적정가가 없어도 실제 매물 가격·정책·예산을 충족하면 가능합니다. 적정가 대비 할인 조건이 있으면 유효한 실제 가격 자료가 필요하며, 자료 부재·만료·변형 불일치 시 결제를 보류합니다. Mock 적정가는 실제 테스트넷 결제를 허용하는 근거로 쓰지 않습니다.

가격 관측은 72시간 이내, 환율을 사용했다면 환율 관측은 24시간 이내를 유지합니다. 세트·언어·에디션·상태가 일치해야 하며 프론트에 가격 기준 시각과 보류 사유를 표시합니다. 이는 최대 자료 나이 기준으로서 거래 가격을 보증하지 않습니다.

지정가·시장가 미매칭은 null입니다. 지정가는 대기 유지, 시장가는 해당 시도 종료입니다. 특정 고정가 매물 사용 불가는 LISTING_UNAVAILABLE, 고정가 상한 초과는 PRICE_LIMIT_EXCEEDED, 정책·예산 위반은 각각 명시적 오류입니다.

### 10.3. 요청 키

서버 실행 계층이 작업별 멱등 키를 생성·보관하고 MCP로 전달합니다. 같은 작업의 통신 재시도는 같은 키, 새 주문 의도와 미매칭 후 새 시장 탐색은 새 키를 사용합니다. 같은 키를 다른 인수에 재사용하면 오류입니다. LLM이 키를 생성·변경하지 않으며 UNKNOWN 결제를 새 키로 우회 재지급하지 않습니다. 요청 키는 HTTP Idempotency-Key, 지급 서명은 params._meta["x402/payment"]를 사용합니다. 전체 DTO와 구현 범위는 API 계약서·합의 사항을 따릅니다.

### 11.5. 최종 검증 시나리오

**시나리오 A — 고정가 즉시 구매**

1. 사용자가 특정 카드 구매를 요청한다.
2. Agent가 카드 검색 및 적정가를 분석한다.
3. 조건에 적합한 고정가 매물을 선택한다.
4. MCP를 통해 카드 예약 및 x402 결제를 실행한다.
5. 정산 성공 후 카드 소유권이 이전된다.

**시나리오 B — 매수 지정가 주문**

1. Agent가 최대 구매 가격을 설정한다.
2. 조건에 맞는 매물이 없어 매수 주문을 대기시킨다.
3. 가격 조건을 만족하는 매물이 등록된다.
4. Agent 활성 상태와 예산 정책을 확인한다.
5. 구매·결제·소유권 이전을 완료한다.

**시나리오 C — 시장가 구매**

1. Agent가 최대 지급 가격을 포함한 시장가 구매를 요청한다.
2. Trading Engine이 최저가 매물을 조회한다.
3. 가격 조건이 충족되면 예약 및 결제를 진행한다.
4. 조건을 만족하지 않으면 구매하지 않는다.

**시나리오 D — 안전성 및 장애 복구**

1. 예산 초과 구매 요청을 차단한다.
2. 동일 카드의 동시 구매를 방지한다.
3. 결제 결과가 불명인 경우 중복 지급을 중지한다.
4. 정산 성공 후 DB 반영 실패 시 결제 재실행 없이 소유권 이전을 복구한다.
5. Agent 중단 시 신규 거래 실행을 멈춘다.

## 12. 최종 성공 기준

최종 시스템이 완성되었다고 판단하기 위해 다음 조건을 충족해야 한다.

1. AI Agent가 OpenAI API를 통해 자연어 구매 지시를 해석한다.
2. MCP SDK v2를 이용하여 카드·거래 도구를 호출한다.
3. Agent가 적정가와 승인된 구매 조건에 따라 거래 전략을 선택한다.
4. Trading Engine이 카드 예약과 매칭을 정상 처리한다.
5. x402로 테스트 USDC 결제가 실제 정산된다.
6. 정산 성공 이후 내부 카드 소유권이 정확히 한 번 이전된다.
7. 예산 초과, 중복 구매, 결제 실패에 대해 안전하게 동작한다.
8. 전체 시나리오를 웹에서 시연할 수 있다.
9. 연구 담당자가 실행 결과와 시스템의 한계를 분석할 수 있다.

**프로젝트의 최종 산출물은 복잡한 거래소 자체가 아니라, AI Agent의 자율적인 구매 판단부터 실제 테스트넷 지급 및 거래 완료까지 연결되는 통합 PoC 시스템이다.**
