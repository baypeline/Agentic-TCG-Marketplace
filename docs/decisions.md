# 거래·예산·Agent 실행 합의 사항

확정일: 2026년 11월 24일. 사용자가 제공한 시스템 설계서 v2.1·API 계약서 v2.0·기획안을 검토한 뒤, 이번 대화에서 사용자와 하나씩 결정한 업무 규칙입니다. 다른 담당자에게 공유·배포가 완료됐다는 의미는 아닙니다.

반영 문서는 [시스템 설계서 v2.2](system-design.md)와 [API 계약서 v2.1](api-contract.md)입니다. 첨부 원본은 변경하지 않습니다. 아래 합의의 코드 반영 현황은 뒤의 표로 구분합니다. 구체적인 경로·DTO·설정은 [통합 가이드](trading-integration.md)를 참고합니다.

## 1. 정책별 누적 예산

총예산·사용 완료액·결제 예약액은 정책 ID에 결합합니다. Agent 중단·재시작·새 세션·정책 수정으로 누적 사용액을 초기화하지 않습니다. 같은 정책을 쓰는 여러 세션은 예산을 공유합니다.

`사용 가능 예산 = 총예산 − 사용 완료액 − 결제 예약액`

카드만 예약하고 결제를 제출하지 않은 금액은 결제 예약액에 포함하지 않습니다. 제출 승인 시 예산을 예약하고, 정산 성공 시 사용 완료액으로 전환하며, 확정 실패 시 예약액을 반환합니다. UNKNOWN 동안에는 예약액을 유지합니다. 지갑 잔액 확인과 정책 예산 검사는 별개입니다.

## 2. 정책 변경 시 기존 예약 유지·결제 보류

정책 수정만으로 이미 확보한 카드 예약을 자동 취소하지 않습니다. 최신 조건에 어긋난 예약은 유지하되 결제를 보류합니다. 프론트는 사유와 필요한 사용자 조치를 안내합니다. 사용자는 정책을 조정하거나 예약을 취소할 수 있습니다. 변경 전 정책으로 자동 결제하지 않습니다.

## 3. 보류 예약의 원래 만료 시간 유지

정책 변경이나 Agent 중단으로 보류해도 기존 expiresAt을 연장하지 않습니다. 프론트에 남은 시간을 표시하고, 시간 안에 조건이 충족되면 최신 정책·예산을 재검증한 뒤 결제할 수 있습니다. 결제 미제출 상태로 만료되면 예약을 해제합니다. 현재 기본 예약 TTL 2분은 그대로 둡니다. 제출 승인이 확정된 결제에는 이 만료 해제 규칙을 적용하지 않습니다.

## 4. 결제 제출 승인 경계

마켓플레이스 서버가 다음 순서로 처리합니다.

1. 최신 정책·예산·카드 예약 유효성을 재검증합니다.
2. 결제 시도·예산 예약·카드 보호 상태·적용 정책 버전을 같은 DB 트랜잭션에 저장합니다.
3. 제출 승인 커밋 이후 Facilitator에 외부 정산 요청을 전송합니다.

이 서버 DB 커밋을 예약 보호와 복구 대상 판정의 경계로 사용합니다. 단순한 결제 요구 발행·브라우저 클릭 시각을 제출 승인으로 취급하지 않습니다. 네트워크 요청을 DB 트랜잭션에 포함해 원자성이 생긴다고 가정하지 않습니다.

## 5. UNKNOWN의 보호와 서버 복구

정산 결과가 불명확하면 새 결제 시도·새 지급 서명을 만들지 않고 카드·예산 예약을 유지합니다. 마켓플레이스 서버가 기존 증빙으로 상태를 조회·복구합니다. 프론트는 “결제 확인 중”으로 표시하고 재결제를 차단합니다.

성공 확인 시 소유권 이전을 진행하고, 확정 실패 시 카드 예약을 해제하고 예산 예약액을 반환합니다. 시간 경과만으로 실패 처리하지 않습니다. 장기 미확정은 운영자 확인 대상으로 넘기되 결과가 확정될 때까지 보호를 유지합니다.

## 6. 결제와 거래 상태 분리

Payment의 SETTLED는 지급 정산 성공입니다. 이때 예산 예약액을 사용 완료액으로 바꿉니다. 소유권 이전 전에는 “결제 완료 · 거래 처리 중”으로 표시하며, 소유권 이전과 Trade 저장이 모두 끝나야 “구매 완료”입니다.

거래 반영 실패 시 추가 결제 없이 소유권 이전·Trade 저장만 멱등 재시도합니다. 복구가 지연되면 운영자 확인 대상으로 넘기며 카드는 보호합니다. 예를 들어 결제 SETTLED와 거래 FINALIZING은 동시에 표현할 수 있어야 합니다. 전체 상태 enum과 조회 응답 필드는 세부 계약에서 별도 고정합니다.

## 7. 서버가 Agent 실행 수명 관리

브라우저·네트워크·SSE 연결 종료는 Agent 실행 중단 사유가 아닙니다. 서버가 LLM 작업과 구매 실행 수명을 관리하며, 브라우저는 상태를 조회·구독하고 재접속 시 기존 실행 상태를 받습니다. 명시적 제어 요청과 조회 연결 종료를 구분합니다.

명시적 중단·서버 실행 기한 만료·정책 비활성화 시 신규 거래 실행을 중지합니다. 브라우저 대화 연결의 유휴 시간과 구매 실행 기한을 동일하게 취급하지 않습니다.

## 8. Agent 중단·재개 규칙

| 중단 시점의 대상 | 처리 |
| --- | --- |
| 대기 지정가 주문 | PAUSED로 전환하고 재개 가능 |
| 결제 미제출 카드 예약 | 유지, 결제 보류, 원래 만료 시간 유지 |
| 제출 승인된 결제 | 카드·예산 보호와 정산 확인·거래 복구 계속 |

재개 시 최신 정책과 예산을 재검증합니다. Agent 중단을 이유로 기존 미제출 예약을 즉시 해제하지 않습니다. 예약이 만료되어 해제돼도 중단된 대기 주문을 자동 재개하지 않습니다. 여러 세션이 같은 Agent를 공유할 때의 서버 실행 소유 관계는 구현 단계에서 명시하며, 브라우저 연결 수로 online을 판정하지 않습니다.

## 9. 총예산 감액 하한

총예산을 사용 완료액 + 결제 예약액보다 낮추는 수정은 거부합니다. 사용 완료 20 USDC·제출된 결제 예약 7 USDC라면 총예산 하한은 27 USDC입니다. 총예산을 28 USDC로 바꾸면 새로 사용 가능한 금액은 1 USDC입니다. 추가 구매를 중지하려면 정책 비활성화 또는 Agent 중단을 사용합니다.

## 10. 정책 변경과 제출 승인의 순서

사용자 클릭 시각이 아니라 서버 DB 확정 순서를 따릅니다. 정책 변경이 먼저 확정되면 최신 정책으로 제출을 검사하고 조건 위반 시 보류합니다. 결제 제출 승인이 먼저 확정되면 해당 결제는 보호·복구 대상으로 유지하고 변경된 정책은 이후 제출 승인부터 적용합니다. 정책 검사·예산 예약·적용 버전 기록은 제출 승인과 같은 DB 트랜잭션에서 처리합니다.

## 11. 카드 ID 유지·이전 이력은 Trade

TRANSFERRED 상태는 제거합니다. 구매 완료 시 동일한 InventoryItem UUID를 유지하면서 ownerId를 구매자로, 상태를 AVAILABLE로 변경합니다. 판매자의 보유 목록에서는 제외하고 이전 소유자·판매 가격·결제 증빙·완료 시각은 Trade로 보존합니다. 소유권 변경과 Trade 저장을 같은 DB 트랜잭션에서 한 번만 처리합니다. 판매자 화면의 “이전 완료”는 거래 이력에서 표시합니다.

## 12. 식별자 이름 통일

객체 자신의 식별자는 id, 다른 객체 참조는 listingId·matchQuoteId·inventoryItemId·policyId 등으로 통일합니다. Listing.id와 MatchQuote.id를 listingId·matchQuoteId라는 응답 별칭으로 중복 제공하지 않습니다. 이 규칙은 Agent 실행 세션의 응답 식별자에도 적용합니다. 실제 식별자는 UUID이며 문서의 짧은 ID 예시는 설명용입니다.

## 13. 구매 조건별 가격 자료 요구

가격 상한만 지정한 구매는 실제 매물 가격·정책·예산이 조건을 충족하면 적정가 없이도 가능합니다. 할인율 조건이 있는 구매는 유효한 실제 적정가가 없으면 보류합니다. Mock 적정가는 실제 테스트넷 지급을 허용하는 근거가 아닙니다.

기존 가격 관측 72시간·환율 관측 24시간 기준을 유지합니다. 카드의 세트·언어·에디션·상태가 일치해야 합니다. 자료 부재·만료·변형 불일치를 조건 충족으로 처리하지 않으며, 프론트에 가격 기준 시각과 보류 사유를 표시합니다. 이 기간은 자료의 최대 나이 기준이며 가격 보증이 아닙니다.

## 14. 서버 실행 계층이 멱등 키 소유

서버 실행 계층이 작업별 키를 생성·보관하고 MCP 호출에 전달합니다. 같은 작업의 응답 유실·통신 재시도는 같은 키를 사용합니다. 사용자 새 주문 의도와 미매칭 후 새 시장 탐색은 새 키를 사용합니다. 같은 키의 다른 인수는 오류입니다. LLM이 키를 생성·변경하지 않으며 UNKNOWN 결제를 새 키로 우회 재지급하지 않습니다.

## 15. 정책 ID와 버전

정책마다 고유 id를 부여하고 수정 시 같은 id의 version을 증가시킵니다. 이전 버전은 보존합니다. 세션은 policyId를 참조하고 제출 승인 기록에는 실제 적용한 policyId·policyVersion을 저장합니다. 누적 사용액과 결제 예약액은 정책 버전이 아닌 정책 ID에 결합합니다.

## 16. 미매칭과 업무 오류

| 상황 | 결과 |
| --- | --- |
| 지정가 조건에 맞는 매물 없음 | null, 주문 대기 유지 |
| 시장가 조건에 맞는 매물 없음 | null, 해당 시도 종료 |
| 특정 고정가 매물이 판매·예약 등으로 사용 불가 | LISTING_UNAVAILABLE |
| 특정 고정가 매물의 가격이 요청 상한 초과 | PRICE_LIMIT_EXCEEDED |
| 정책 위반·예산 부족 | 각각 명시적 업무 오류 |

REST는 직접 DTO 또는 null, MCP 성공은 래퍼의 data에 DTO 또는 null을 넣습니다. 통신·서버 오류를 정상 미매칭으로 바꾸지 않습니다.

## 17. 판매자 모의 수익

완료된 Trade의 판매 가격을 판매자 모의 수익으로 집계합니다. 결제만 성공하고 소유권 이전이 진행 중이면 확정 수익에 포함하지 않습니다. 동일 Trade를 재시도·재처리로 중복 집계하지 않습니다. 별도 출금 가능 잔액을 중복 관리하지 않으며 프론트에 “모의 판매 수익 · 출금 불가”로 표시합니다.

## 현재 구현과 검증 범위

2026년 11월 24일 코드 반영 기준입니다. 업무 규칙과 통합 테스트를 구현했으며, 실제 LLM·지갑을 통한 전체 자동 구매 시연은 별도입니다. Web은 수동 거래 관리와 상태 조회를 연결했습니다.

| 모듈 | 반영 내용 | 검증 |

## 구현 단계에서 정한 세부 계약

정책·예산 REST와 DTO, 결제·거래 중간 상태, MCP 메타데이터는 [API 계약서](api-contract.md)에 명시했습니다. 서버 실행은 같은 Agent의 동시 실행이 같은 정책을 공유하며 실행 기한은 정책 유효 기한과 시작 후 24시간 중 이른 시각입니다. 조회 SSE는 재접속 시 현재 스냅샷을 제공하며 과거 이벤트를 재생하지 않습니다. 기본 복구 주기는 30초, 운영 확인 표시는 미확정/거래 반영 지연 5분부터입니다. `reviewAfterMs`로 기준을 주입할 수 있습니다.

서버 실행 플러그인의 `execute`/Core API의 `executeAgentRun`에 실제 LLM 실행기를 주입해야 자연어 작업이 실행됩니다. 기본 진입점은 정책에 따른 거래 허가와 상태 관리만 제공하며 기존 대화 Runtime의 구매 경로는 Mock 미리보기입니다. 서버 MCP 클라이언트와 `policies.actionKey`는 실제 실행기가 연결할 수 있도록 제공하지만 자동으로 LLM이나 지급 서명기를 선택하지 않습니다. DB 복구는 별도로 계속 동작합니다. 현재 실행 재개는 단일 실행 호스트를 전제로 하며 여러 호스트의 작업 임대·리더 선출은 구현하지 않았습니다.

테스트넷 지급은 명시적인 설정이 필요합니다. 이번 변경의 결제·MCP 통합 검증은 주입한 어댑터를 사용하며 실제 Facilitator 정산을 새로 수행한 증빙은 아닙니다. 트랜잭션 해시가 없는 UNKNOWN은 자동으로 확정할 수 없으므로 운영 확인 대상으로 남기고 카드·예산을 계속 보호합니다. 운영자 강제 해제/실패 처리 API는 제공하지 않습니다.
